## 1. 漫画翻译的四步流水线(基础认知)

真正的沉浸式漫画翻译(译文盖回气泡)是一条流水线:

1. **检测**:找出每块文字的像素坐标(bounding box)
2. **OCR**:把每块文字识别成字符串
3. **翻译**:已有能力
4. **消字 + 嵌字**:擦掉原文像素(inpainting),把译文按气泡重新排版画回去

档位:
- **A**:译文丢侧栏/旁边。漫画场景意义不大(已否决)。
- **B-lite**:不真消字,按坐标盖个匹配底色的框 + 排版译文。气泡多为纯白底,效果接近沉浸式。
- **B-full**:真 inpainting 消字再重绘,背景天衣无缝。质量天花板。

## 2. 已验证的事实(实测,非推测)

测试工具:`_vision_test/test.py`(零依赖,标准库 urllib)。
测试图:少年Jump+《スレイブの誕生》第1话某页(全屏截图)。
模型:`mimo-v2.5`(小米官方 `https://token-plan-cn.xiaomimimo.com/v1`,OpenAI 兼容)。

### ✅ 发现 1:mimo-v2.5 的 OCR + 翻译 = 满分
- 日文识别全对,连竖排、拟声词(ハイル/ふゆふゆ)都识别。
- 中文翻译又准又地道,语气拿捏到位。
- **结论:翻译这步,mimo-v2.5 完全可以独当一面。**

### ❌ 发现 2:mimo-v2.5 的 grounding(出坐标)= 不可用(漫画场景)
- 让它同时给 bbox,坐标大面积偏移:整页 ~11 块里 7~8 块会把译文盖到错误画面上。
- 裁掉全屏截图的黑边(letterbox)后,"框飞出画面"修好了,但**框本身找不准依旧**。
- 这是 **VLM 固有短板**,不是 prompt/参数问题:grounding 在 GUI/自然照片上强(MiMo 强项也在此),
  但漫画"一页十几个小气泡、非网格排布、竖排 + 手写拟声词"是 grounding 最难场景。

### 🔑 核心结论
> **"找文字在哪" 和 "文字是什么" 必须拆开,交给不同工具。**
> LLM 干不了精确坐标 → 检测必须用**专用检测器**。这正是成熟方案
> [manga-image-translator](https://github.com/zyddnys/manga-image-translator) 的做法。

### 旁支发现:目标站点反爬
- 少年Jump+ 把漫画图打散成小块、用 canvas 重新拼显示,DOM 里的 `<img>` 是乱序碎片/空白。
- → 这类站"插件直接读 `<img>` src"行不通,将来要**抓 canvas 渲染结果**。很多别的站没这问题。
- 也因此本地测试只能用截图(无法下载 raw 图)。

## 3. 推荐架构(给定 3060 + 求效果)

**本地完整管线 + 插件瘦客户端**。直奔 B-full 真嵌字。

```
浏览器插件(瘦客户端)
   │  抓图(普通站读 <img> / 反爬站抓 canvas)
   ▼
localhost 后端 = manga-image-translator(在 3060 上跑)
   ├─ 检测:comic-text-detector        (本地 GPU)  ← 解决发现 2 的坐标问题
   ├─ OCR :manga-ocr                   (本地 GPU)  ← 日文专用,准
   ├─ 翻译:mimo-v2.5 (OpenAI 兼容 API)            ← 已验证满分;或本地模型
   ├─ 消字:lama (inpainting)           (本地 GPU)  ← 真 B-full
   └─ 嵌字:排版译文回气泡              (本地)
   ▼
返回处理好的整图 → 插件叠在原图上(可一键还原)
```

要点:
- manga-image-translator 已集成全部步骤,有 web/API 模式,可暴露 HTTP 接口。
- 它的翻译后端支持自定义 OpenAI 兼容端点 → 直接接 mimo-v2.5(待确认配置项)。
- 3060 Laptop(~6GB)跑 detector + manga-ocr + lama 没问题,注意单次图尺寸/批量别太大。

### 备选(暂不选,留档)
- **路线① 浏览器 WASM 检测器**(onnxruntime-web 跑 comic-text-detector + 盖框 B-lite):
  零后端、可移植,但无 GPU inpainting(只能 B-lite)、bundle 变重。只在将来想"脱离本机也能用"时才考虑。
- **纯 mimo 出坐标**:已否决(发现 2)。

## 6. Phase 1 调研结论(2026-06-15)

以 [manga-image-translator](https://github.com/zyddnys/manga-image-translator) 官方 README 为准。

### 6.1 接 mimo 当翻译后端 —— ✅ 支持,两种接法
- **首选:标准 `openai` translator + base 覆盖**(支持术语表 glossary + json_mode,更成熟):
  - `OPENAI_API_BASE=https://token-plan-cn.xiaomimimo.com/v1`
  - `OPENAI_API_KEY=<mimo key>`
  - `OPENAI_MODEL=mimo-v2.5`
  - translator 选 `openai`(配置枚举名写作 `chatgpt`)
- **备选:`custom_openai`**(env:`CUSTOM_OPENAI_API_BASE` / `CUSTOM_OPENAI_API_KEY` / `CUSTOM_OPENAI_MODEL`)。
  注意:custom_openai **不能加载 glossary**;社区报过本地模型 JSON 解析报错([#1011](https://github.com/zyddnys/manga-image-translator/issues/1011))。
  mimo 已验证返回干净 JSON,风险低,但首选仍是标准 openai。

### 6.2 6GB 显存够不够 —— ✅ 够(关键:翻译走 API,本地不加载 LLM)
- 3060 Laptop 确认是 6GB 版。
- 官方没给显存数字;重头(本地 LLM 翻译)我们用 mimo API → 不加载。
- 剩下检测 + manga-ocr + lama 修复都是小模型,6GB 跑得开。
- OOM 风险点:`inpainting_size` / `detection_size` 太大 → 调小即可。
- **inpainter 用 `lama_large`(默认/推荐),别用 `sd`(stable-diffusion,重)。**
- 启动加 `--use-gpu`;真 OOM 就降分辨率,或个别阶段回退 CPU。

### 6.3 模型选择(漫画)
- 检测 detector:`default` / `ctd`(comic-text-detector);**别用 `craft`(官方说不适合漫画)**。
- OCR:`48px`(默认)或 `mocr`(manga-ocr,日文专用)。
- 修复 inpainter:`lama_large`。

### 6.4 服务 / API 模式
- `cd server && python main.py --use-gpu`
- Web UI `:8000`,API `:8001`,接口文档 `:8000/docs`(Swagger)。
- 也有官方 Docker 镜像。

### 6.5 Windows 安装
- Python 3.10+;需先装 **MS C++ Build Tools**(部分依赖要编译);
- 按 pytorch.org 装对应 CUDA 版 PyTorch(CUDA 12.x,驱动 ≥525)。

### 6.6 🚀 重大发现:现成一键 GUI 封装,Phase 1 可大幅简化
[hgmzhn/manga-translator-ui](https://github.com/hgmzhn/manga-translator-ui) —— 基于 manga-image-translator:
- **Windows 一键装**:双击 `步骤1-首次安装.bat`(无需预装 Python),或解压后双击 `app.exe`。
- CUDA 12.x 支持,CPU 可回退。
- **自带可视化编辑器**:移动/旋转/变形文本框、手动改译、样式调整、mask 编辑 → 嵌字不完美时能手动修。
- 内置 OpenAI/Gemini 等引擎;OpenAI 引擎大概率有 base_url 字段(待实测能否指向 mimo)。

### 6.7 战略提醒(产品形态)
- 反爬站(少年Jump+)抓图难;你又"不限形态、自用、求效果"。
- → 对"读在线漫画"这个场景,**桌面 GUI 工作流(截图/存图 → 喂 app → 出译图)可能比浏览器插件更稳、质量更高**。
- 浏览器插件对"网页普通图片"仍有价值,但漫画主力可考虑走桌面 app。

### 6.8 Phase 1 最省力路径(修订)
1. 先装 hgmzhn 一键 GUI,用本页同款漫画跑通,确认检测/消字/嵌字质量。
2. GUI 里把翻译引擎指向 mimo(OpenAI 引擎 + 自定义 base_url);不行就先用内置/Google 看管线效果,翻译接入单独解决。
3. 管线质量满意后,再决定 Phase 2 是做插件对接,还是以桌面工作流为主。
